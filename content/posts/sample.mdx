This page is a working specimen of the article layout. It brings together the elements that appear in technical writing, from a short `git status` command to wide tables, Kubernetes manifests, terminal output, and nested code blocks. Use the contents navigation to compare sections, then check the same examples in both themes and at narrower widths.

## Typography and inline code

A paragraph should be easy to follow without competing with the navigation. **Strong text** adds emphasis, _italic text_ adds a quieter distinction, and [links remain easy to identify](https://astro.build). A footnote can carry a useful aside without interrupting the sentence.[^layout]

Inline code such as `pnpm run build`, `config.enabled`, and `/etc/loader/loader.conf` should sit comfortably within the line. Longer identifiers such as `a_deliberately_long_configuration_key_that_needs_to_wrap_on_a_small_screen` must stay inside the reading column.

### Links, emphasis, and punctuation

A link inside a sentence should remain identifiable without overpowering the paragraph. Compare an [internal article link](/post/kubernetes-rbac-made-simple/), a [section link](#yaml-and-kubernetes), and a link next to `inline_code`. **Bold with an _italic phrase_**, ~~outdated advice~~, and a keyboard shortcut such as <kbd>Ctrl</kbd> + <kbd>K</kbd> should all have a clear place in the text.

Technical prose also includes symbols and punctuation: “quoted text”, an apostrophe in a developer’s note, an en dash in a range (3–5), arrows →, a percentage (99.9%), and an expression such as <var>n</var><sup>2</sup>. None should change the rhythm of the line.

  2. Run the operation.
  3. Report the outcome.

## Code blocks

Code uses a neutral surface, distinct syntax colors, and the same monospace family as the interface. Language labels and filenames belong in the header. The copy control copies the code, not the header.

```python title="automation.py" {4-6}
from pathlib import Path


def collect_notes(directory: Path) -> list[Path]:
    # Return a predictable order for repeatable builds.
    return sorted(directory.glob("*.md"))


notes = collect_notes(Path("content/posts"))
print(f"Found {len(notes)} notes")
```

### YAML and Kubernetes

YAML is common in infrastructure articles. Keys should be visually distinct from string values; punctuation, comments, numbers, and booleans should remain easy to tell apart. This first example mirrors a practical RBAC manifest, including nested mappings and arrays.

```yaml title="pod-reader.yaml"
# Allow a reader to inspect pods in one namespace.
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: default
  labels:
    app.kubernetes.io/part-of: documentation
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs:
      - get
      - list
      - watch
```

### Workflow YAML and expressions

CI configuration adds expressions, environment variables, shell commands, and multiline values. The workflow expression syntax below is literal code, not part of the article renderer.

```yaml title=".github/workflows/validate.yml"
name: Validate content
on:
  pull_request:
    paths: ["content/**", "src/**"]
permissions:
  contents: read
jobs:
  validate:
    runs-on: ubuntu-latest
    env:
      CI: true
      BRANCH: ${{ github.head_ref }}
    steps:
      - uses: actions/checkout@v4
      - name: Check generated content
        run: |
          printf 'Validating branch: %s\n' "$BRANCH"
          pnpm run build
```

### TypeScript and JavaScript

Compare type annotations, property names, function calls, strings, and template substitutions. Comments should stay quieter than executable code.

```typescript title="validate-entry.ts"
type Entry = {
  title: string
  draft?: boolean
  tags: string[]
}

export function describeEntry(entry: Entry): string {
  const visibleTags = entry.tags.filter((tag) => tag.length > 0)
  // Keep the display label separate from the stored title.
  return `${entry.title}: ${visibleTags.join(", ") || "untagged"}`
}

const entry: Entry = { title: "A useful automation", draft: false, tags: ["python"] }
console.log(describeEntry(entry))
```

```javascript title="retry.js"
export async function retry(operation, attempts = 3) {
  for (let attempt = 1; attempt <= attempts; attempt += 1) {
    try {
      return await operation()
    } catch (error) {
      if (attempt === attempts) throw error
      await new Promise((resolve) => setTimeout(resolve, 250 * attempt))
    }
  }
}
```

### Shell scripts and errors

A shell example should distinguish comments, variables, flags, and quoted strings. These are illustrative commands; no script on this page is executed by the browser.

```bash title="scripts/check-content.sh"
#!/usr/bin/env bash
set -euo pipefail

content_dir="${1:-content/posts}"
if [[ ! -d "$content_dir" ]]; then
  printf 'Missing directory: %s\n' "$content_dir" >&2
  exit 1
fi

find "$content_dir" -type f -name '*.mdx' -print |
  sort |
  while IFS= read -r file; do
    printf 'Checking %s\n' "$file"
  done
```

### SQL and patches

A query mixes keywords, identifiers, string literals, and numeric values. A patch should make additions and removals distinguishable.

```sql title="recent-articles.sql"
SELECT title, published_at, category
FROM articles
WHERE draft = FALSE
  AND category IN ('engineering', 'guides')
ORDER BY published_at DESC
LIMIT 5;
```

```diff title="navigation.patch"
-const visiblePosts = posts.filter((post) => post.featured).slice(0, 6)
+const featured = posts.find((post) => post.featured)
+const visiblePosts = (featured
+  ? [featured, ...posts.filter((post) => post.id !== featured.id)]
+  : posts).slice(0, 5)
```

### Highlighted lines and untitled blocks

Highlighted ranges should fill the code area evenly without introducing extra blank lines. This example has two separate ranges, including a nested block.

```python title="validation.py" {2-3,6-7}
def validate(title: str, retries: int) -> bool:
    if not title.strip():
        raise ValueError("A title is required")

    for attempt in range(retries):
        print(f"Validation attempt {attempt + 1}")
        return True
    return False
```

### Callout variants

Each supported callout has the same geometry and spacing. Its icon and semantic color distinguish the message, rather than a different card design.

<Callout variant="tip" title="Start with a small input">

</Callout>

</Callout>

<Callout variant="important" title="Keep the original context">

</Callout>

</Callout>

### Optional details

Native disclosure elements can hold a longer explanation without interrupting the first reading. Check both the closed and expanded states.

<details>
  <summary>Why keep a small reproduction?</summary>
  <p>A short example makes it easier to separate a rendering problem from an issue in the source content. It also gives the next person a concrete case to verify.</p>
  <p>Include the relevant configuration, the expected result, and what actually happened. Keep unrelated details out of the reproduction.</p>
</details>
